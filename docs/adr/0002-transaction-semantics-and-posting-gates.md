# ADR-0002：统一交易语义与自动入账门禁

- 状态：Accepted
- 日期：2026-08-23
- 决策者：项目所有者

## 背景

金额方向不足以描述支付业务。同为支出可以是消费、手续费或红包；信用卡还款和账户间转账都应表现为双账户转账；退款和红包退回还需要关联原交易。通知解析器和 AI 可以理解文本，但不能各自决定最终会计行为。

项目所有者已确认采用智能自动入账，并要求简单场景按主流记账逻辑处理，同时保留自动去重和异常待确认门禁。

## 决策

在候选契约中同时记录：

- `direction`：`expense`、`income`、`transfer`、`refund` 或 `unknown`；
- `transactionKind`：消费、普通收入、退款、转账、信用卡还款、红包发出/收到/退回、手续费、预授权或未知。

所有语义映射只在 `beecount_automation_core` 中实现：

| 交易类型 | 方向 | 自动入账附加条件 |
|---|---|---|
| 消费、手续费、红包发出 | 支出 | 满足通用金额、账户、证据和去重门禁 |
| 普通收入、红包收到 | 收入 | 满足通用门禁 |
| 退款、红包退回 | 退款 | 必须关联原交易 |
| 转账、信用卡还款 | 转账 | 必须解析出两个不同账户 |
| 预授权 | 支出候选 | 永不直接入账，等待最终扣款或人工确认 |
| 未知或组合/分期等未定义场景 | 未知 | 进入待确认，不猜测 |

通知规则和 AI 只能提出候选类型、方向及证据。自动入账决策还必须验证二者一致，且 `transactionKind` 有来源证据。AI 置信度不能跳过任何门禁。

BeeCount 当前正式交易只支持支出、收入和转账。扩展因此显式生成 `HostTransactionType`：退款和红包退回创建一笔新的收入交易，同时由扩展候选/入账回执保存 `relatedTransactionId`；禁止修改或删除原支出。未来若 BeeCount 原生支持退款关系，只能通过新的 Bridge ADR 迁移，不能改变现有账务结果。

## 后果

- 简单高频交易可以稳定自动入账。
- 信用卡还款不会误记成支出，退款不会在缺少原交易时静默冲销。
- 一个来源明确包含消费与手续费时，解析器可以输出两笔候选；无法安全拆分的组合支付或分期进入待确认。
- 新增交易语义时必须先扩展 Core 的表驱动规则和测试，再由解析器输出，不得只改提示词或 Kotlin。
- 当前契约尚未发布，因此在 schema v1 冻结前补入必填字段，不产生已发布数据迁移。

## 隐私与权限影响

本决策不新增权限或网络行为。交易类型是最小化结构化字段；原始文本仍不进入候选 JSON、日志、同步或导出。

## 回滚策略

可关闭自动入账总开关，使所有候选只进入待确认。不能通过删除语义门禁来提升自动入账率。
